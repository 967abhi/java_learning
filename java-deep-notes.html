    01

    Class, object & where they live

    oops/Firstoops.java

    The blueprint / entity line · stack vs heap · what new really does

    • Class is the blueprint, object is the real-world entity. Getting this the wrong way round is the single most common slip in a first answer — a class is a template, it is not a thing.
    • A class holds exactly two kinds of member: state (fields / properties) and behaviour (methods).
    • Car c1 = new Car(); is three separate events: Car c1 declares a reference variable of a user-defined type, new allocates the object on the heap, and = stores the object's address in the reference.
    • The reference lives on the stack, the object lives on the heap. That one sentence is the foundation for call-by-value, garbage collection, and every NullPointerException you will ever explain.
    • A reference can exist with no object behind it — Car c1 = null; is a valid stack slot pointing nowhere. Touching it is the NPE.

    Sizing an object (the question behind “how much memory?”)

    class Student {
    String name;      // reference → 4 bytes (compressed oops)
    String college;   // reference → 4 bytes
    String city;      // reference → 4 bytes
    int    roll;      // value     → 4 bytes
}
→ ~16 bytes of fields in the heap
// the String objects themselves are separate heap objects;
// this count is only the size of the references.
    Say it out loud

    A class is a blueprint; an object is an instance of it on the heap. The variable you hold is only a reference on the stack.

    02

    Constructors, overloading & chaining

    oops/chainingConstructor.java

    Three types · why overloading is not chaining · the this keyword

    • A constructor has the same name as the class, no return type at all (not even void), and runs automatically on new. Writing return name; inside one is a compile error.
    • Three flavours: default (Java supplies one only if you write none), parameterised, and copy (takes another object of the same class and copies its fields).
    • Constructor overloading = several constructors, same name, different parameter lists. Resolved at compile time.
    • Constructor chaining = one constructor calling another with this(...), or calling the parent with super(...). Either call must be the first statement in the constructor, so you can never use both in one constructor.
    • this is a reference to the current object — needed the moment a parameter shadows a field: this.name = name;
    // overloading — five constructors, five signatures
Student(){ ... }
Student(String name){ ... }
Student(String name, int age){ ... }

// chaining — one constructor delegating to another
Student(String name){
    this(name, 18);          // must be the FIRST line
}
    The traps
    • Write any constructor yourself and the free default constructor disappears. new Student() then stops compiling until you add it back.
    • If you do not call super(...), the compiler inserts a silent super() — so a parent with only a parameterised constructor breaks every child until the child calls super(args) explicitly.
    • Overloading is decided by the declared type of the argument, at compile time. Overriding is decided by the actual object, at runtime. Interviewers mix these two deliberately.
    Can a constructor be final, static or abstract?

    No, none of the three. final is meaningless because a constructor is never inherited, so it can never be overridden. static contradicts its job — a constructor exists to initialise one specific instance and needs this. abstract would mean “no body”, but a constructor must run to build the object.

    It can be private — that is exactly how the singleton pattern and static factory methods like Integer.valueOf() stop you calling new.

    Say it out loud

    Overloading is many constructors; chaining is one constructor calling another with this(...) as its first statement.

    Call by value ★

    oops/callByValue.java

    The one where nearly everyone says “pass by reference” and loses the point

    • Java is always pass by value. There is no pass-by-reference anywhere in the language.
    • For a primitive, the value itself is copied into the method's own stack frame — which is why you cannot write a working swap(int a, int b) in Java.
    • For an object, the thing copied is the reference value (the address). The copy points at the same heap object, so mutating through it is visible outside.
    • But reassigning the parameter only re-points the copy. The caller's reference never moves — and that is the proof it was pass-by-value all along.
    void change(Student s){
    s.name = "CHANGED";      // visible outside — same heap object
    s = new Student("Raj");  // invisible outside — only the copy moved
}
    Then why does everyone say Java passes objects by reference?

    Because the effect of mutating a field looks identical to pass-by-reference. The difference only shows up on reassignment. In a true pass-by-reference language (C++ with &), reassigning the parameter would change the caller's variable too. In Java it never does.

    The precise sentence: Java passes the value of the reference, not the reference itself.

    One level down — what the JVM actually does

    Each method call pushes a frame onto that thread's stack. A frame holds a local variable array and an operand stack, both sized at compile time and recorded in the class file. Parameters are simply the first slots of the callee's local variable array.

    “Copying” is literal: the bytecode is iload_1 (push the int) or aload_1 (push the reference) in the caller, then the invoke instruction moves those operand-stack values into the callee's slots. There is no instruction anywhere in the JVM that would let the callee write back into the caller's slot — which is why pass-by-reference is not merely absent from Java, it is unrepresentable.

    A reference slot is 4 bytes with compressed oops (the default under a ~32 GB heap) and 8 bytes without. That is why the same object graph can get measurably larger on a very big heap — the JVM loses the compression and every reference doubles.

    Where it stops being true-ish: the JIT's escape analysis can prove an object never leaves the method and then scalar-replace it — the object is never allocated at all, its fields living in registers. The semantics you reason about are unchanged; the heap allocation you assumed simply is not there.

    In production

    The bug this causes is not swap(). It is a method that takes a caller's List or Date, mutates it as a “convenience”, and the caller never sees it coming — the change is invisible at the call site because the argument was passed, not returned.

    The senior habit: a method either returns a new value or documents that it mutates its argument. Never both, never silently. This is the same instinct that makes defensive copies necessary in the immutability card.

    Say it out loud

    Java is always pass by value. For objects the reference value is copied — so mutation escapes the method, reassignment does not.

    04

    static, blocks & class loading

    oops/Static.java

    One shared copy · why main is static · the order things run in

    • static means the member belongs to the class, not to any object: one copy shared by every instance, reached by class name — Student.college, not s1.college.
    • A static method has no this, so it cannot touch instance fields or call instance methods directly. It has no object to ask.
    • An instance block { ... } runs before the constructor body, every time an object is created. A static block static { ... } runs once, when the class is first loaded — before main.
    • public static void main(String[] args) is static so the JVM can call it without creating an object first. args carries command-line input: java Demo hello 5 → args[0]="hello", args[1]="5" — always Strings.

    Initialisation order, once and for all

    static fields & static blocks   — once, at class load, top to bottom
        ↓
instance fields & instance blocks — every new object, top to bottom
        ↓
constructor body                 — every new object, last
    The traps
    • A static method cannot be overridden. Redeclaring it in a child is method hiding, and it resolves by the reference type, not the object.
    • static variables are shared, so one object changing it changes it for all — the usual source of “why did my counter jump?”.
    • Instance blocks are copied into every constructor by the compiler, so with three constructors the block still runs exactly once per object.
    One level down — class loading

    “Runs at class load” is the shorthand. The real sequence is load → link (verify, prepare, resolve) → initialise. During prepare, static fields are given their default values (0, false, null). Only during initialise does the JVM run <clinit> — a synthetic method the compiler builds from your static field assignments and static blocks, in source order.

    Initialisation is lazy and triggered: first new, first static method call, first non-constant static field access, or reflection. Reading a static final compile-time constant triggers nothing at all — the value was inlined into your class file, which is why changing a constant in a library and not recompiling the caller leaves the old value baked in.

    <clinit> is run under a lock, exactly once, and the JVM guarantees it. That is the foundation of the holder idiom — a lazily initialised, thread-safe singleton with no synchronisation you have to write:

    class Config {
    private static class Holder { static final Config INSTANCE = new Config(); }
    static Config get(){ return Holder.INSTANCE; }   // loaded on first get(), never before
}
    In production
    • Static mutable state is the memory leak you will actually meet. A static Map cache is reachable from a GC root for the life of the class loader — nothing you put in it is ever collected unless you remove it. In an app server this leaks across redeploys.
    • Static state is shared across threads with no synchronisation. A static SimpleDateFormat is the classic production bug: it is mutable and not thread-safe, so under load it silently returns wrong dates rather than throwing.
    • An exception inside a static block becomes ExceptionInInitializerError, and every later use of that class throws NoClassDefFoundError with no hint of the original cause. Keep static initialisers trivial.
    Say it out loud

    static = one copy, owned by the class, loaded before any object exists.

    Encapsulation

    oops/Encapsulation.java

    Data hiding · and the benefit that is not the getter/setter ceremony

    • Definition: binding data and the methods that act on that data into one unit, and hiding the data from direct outside access. Also called data hiding.
    • How: fields private, access through controlled public getters and setters.
    • The real benefit is validation inside the setter — not the ceremony. Without it anybody writes s.age = 500 and your object is now lying.
    • Getter with no setter → read-only field. Setter with no getter → write-only (a password field, say).
    • The compile error “The field BankAccount.balance is not visible” when you touch a private field from outside is the proof encapsulation is working.
    class BankAccount {
    private double balance;                // hidden state

    public void setAge(int age){
        if (age > 100) {                    // ← this line is the whole point
            System.out.println("Age is not valid");
        } else {
            this.age = age;                // only valid data reaches the field
        }
    }
    public double getBalance(){ return balance; }
}
    Encapsulation vs abstraction — in one line each?

    Encapsulation hides data (the what is stored) using access modifiers. Abstraction hides implementation (the how it works) using abstract classes and interfaces.

    A car: encapsulation is that you cannot reach into the fuel tank and set its level; abstraction is that the pedal works without you knowing whether the engine is petrol or electric.

    Say it out loud

    Encapsulation is private data plus a public gate — and the gate is where the rules live.

    Inheritance

    oops/Inheritance.java

    Five types, one of them illegal · super · what is not inherited

    • extends gives the child the parent's fields and methods — code reuse, and an is-a relationship.
    • Types: single (A→B), multilevel (A→B→C), hierarchical (A→B and A→C). Multiple inheritance of classes is not allowed — the diamond problem — and hybrid follows from that. Interfaces are how Java gives you both anyway.
    • super.field / super.method() reach the parent version; super(...) calls the parent constructor and must run first, always.
    • Not inherited: constructors, private members, and anything the access modifier hides. Static members are inherited but are hidden, not overridden.
    Inheritance (is-a)Composition (has-a)
    Written asclass Car extends Vehicleclass Car { Engine engine; }

    Why is multiple inheritance of classes banned but multiple interfaces fine?

    The diamond problem: if B and C both extend A and override show(), and D extends both, the compiler cannot decide which show() D inherits — there are two competing implementations and two sets of state.

    Interfaces traditionally carried no implementation and no state, so there was nothing to conflict. Since Java 8 added default methods the conflict can return — and Java then forces you to resolve it manually with InterfaceName.super.show().

    Polymorphism & dynamic dispatch ★

    oops/Abstraction.java

    One name, many forms · and the field-vs-method rule people always get wrong

    • Compile-time polymorphism = overloading: same method name, different parameter list, in the same class. The compiler picks the version from the declared argument types.
    • Runtime polymorphism = overriding: same signature in parent and child. The JVM picks the version from the actual object. Mark it @Override so a typo becomes a compile error instead of a silent second method.
    • Overriding rules: same name and parameters; return type same or covariant; access cannot be narrowed; checked exceptions cannot be broadened.
    • Cannot be overridden: static (that is hiding), private (not visible), final (sealed by design).
    • Upcasting — Parent p = new Child(); — is implicit and always safe. Downcasting is explicit and can throw ClassCastException, so guard it with instanceof.
    OverloadingOverriding
    Wheresame classparent and child
    Signaturemust differmust be identical
    Return typefreesame or covariant
    Resolvedcompile time (static binding)runtime (dynamic binding)
    Also calledcompile-time polymorphismruntime polymorphism
    One level down — how dispatch is implemented

    The compiler emits one of four invoke instructions, and knowing which explains every rule above:

    • invokestatic — static methods. Bound at compile time from the reference type. This is why a static method cannot be overridden: there is no object in the instruction.
    • invokespecial — constructors, private methods, super.x(). Also bound at compile time, which is exactly why private methods are invisible to overriding.
    • invokevirtual — normal instance methods. The JVM looks up the method in the object's class vtable at runtime. That lookup is polymorphism.
    • invokeinterface — calls through an interface reference; same idea, slightly costlier lookup because a class can implement many interfaces.

    Fields use getfield, which carries the field's owning class resolved from the declared type. Different instruction, different binding time — that is the whole field-vs-method asymmetry, not a special rule to memorise.

    The JIT then usually erases the cost: if only one implementation has ever been loaded, it inlines the call and leaves a class-hierarchy-analysis guard behind. Virtual dispatch in hot code is often free — until a second subclass loads and the call site becomes bimorphic, then megamorphic.

    Design note — the rules that catch people at review
    • Never call an overridable method from a constructor. The parent constructor runs first, so the child's override executes while the child's fields are still at their defaults — a final field can be observed as null.
    • Covariant returns are allowed; covariant parameters are not. Change a parameter type and you have written an overload, and it will silently never be called. @Override is the only thing that catches this.
    • Overload resolution prefers widening over boxing over varargs. Given f(long) and f(Integer), the call f(1) picks f(long). Overloading on types that box into one another is a design smell for exactly this reason.
    Say it out loud

    Methods are resolved at runtime by the object; fields and statics at compile time by the reference.

    Abstraction: abstract class vs interface

    oops/AbstractClass.java · Interface/

    The comparison table, then the “which would you pick” follow-up

    • Abstraction shows the essential and hides the implementation. Achieved two ways: an abstract class (0–100% abstract) or an interface (100% abstract, traditionally).
    • One abstract method forces the whole class to be abstract. An abstract class cannot be instantiated, but it can have constructors, fields, static and concrete methods — and its constructor does run when a child object is built.
    • A child must override every abstract method, or be declared abstract itself.
    • Interface methods are implicitly public abstract, so the implementing class must declare them public — visibility can never be reduced. Interface variables are implicitly public static final, so they must be initialised where they are declared.
    • An interface can extend another interface; a class implements many. Since Java 8 an interface may also carry default and static methods, and since Java 9, private ones.

    Which one do you actually pick?

    Abstract class when there is shared state and shared code between genuinely related types — Car with a fuel level and a common start().

    Interface when the thing is a capability that unrelated classes can each claim — Comparable, Runnable, Serializable. A class can only extend one parent, so spending that single slot is a real cost.

    Follow-up worth volunteering: an interface with exactly one abstract method is a functional interface, and that is the door into lambdas.

    Say it out loud

    Abstract class = partial implementation with state. Interface = a contract you can sign many times.

    The Object class contract ★

    ObjectClass/Demo1.java

    Every class extends it · and equals/hashCode is where collections break

    • Every class in Java extends java.lang.Object, directly or indirectly. If you write no extends, the compiler adds it — which is why super() in a top-level class calls Object's constructor.
    • The methods you inherit: equals(), hashCode(), toString(), getClass(), clone(), finalize() (deprecated), plus wait(), notify(), notifyAll().
    • Default equals() is == — reference identity. Default hashCode() is derived from the object's identity. Default toString() prints ClassName@hexHashCode.
    • The contract: if a.equals(b) is true then a.hashCode() == b.hashCode() must be true. The reverse is not required — equal hash codes are just a collision.
    • So override equals() and you must override hashCode(). Break this and your key goes into one bucket and gets looked up in another, and the object silently vanishes from every HashMap and HashSet.
    @Override
public boolean equals(Object o){
    if (this == o) return true;
    if (o == null || getClass() != o.getClass()) return false;
    Student s = (Student) o;
    return roll == s.roll && Objects.equals(name, s.name);
}

@Override
public int hashCode(){ return Objects.hash(name, roll); }   // same fields, both methods
    The traps
    • public boolean equals(Student s) is an overload, not an override — the parameter must be Object. This is exactly what @Override catches.
    • Use the same fields in both methods, and only fields that do not change while the object is a key — mutating a key after insertion loses it just as badly.
    • == on objects compares references; .equals() compares value if the class overrode it. String did; your class did not until you write it.
    One level down — the five clauses nobody recites

    equals is not “compare the fields”. It is an equivalence relation with five obligations, and each one is a real bug when broken:

    • Reflexive — x.equals(x). Break it and list.contains(x) returns false for an element that is in the list.
    • Symmetric — x.equals(y) iff y.equals(x). Broken constantly by a subclass that adds a field and compares with instanceof: the parent says equal, the child says not, and the answer now depends on argument order.
    • Transitive — the reason you cannot add a value-carrying field in a subclass and keep a correct equals. This is why the JDK favours composition here.
    • Consistent — the same answer every time, so never involve a mutable field, a clock, or a network call.
    • Non-null — x.equals(null) is false, never a NullPointerException.

    getClass() vs instanceof is the classic trade-off: getClass() keeps symmetry but breaks Liskov substitution (a proxy or a Hibernate subclass will never equal its own entity); instanceof preserves substitutability but cannot stay symmetric once a subclass adds state.

    In production — where hashCode really costs you
    • A constant hashCode() is legal and catastrophic. return 1; satisfies the contract perfectly and turns every HashMap into a single bucket — O(1) becomes O(n), or O(log n) once treeification saves you. Correctness tests pass; the service falls over at scale.
    • A mutable key is a leak. Put an object in a HashSet, then change a field used by hashCode(): it now hashes to a different bucket, so contains() is false, remove() fails, and the entry is unreachable but never collected.
    • Hibernate and JPA make this concrete: an entity's generated id is null before persist and set afterwards, so an id-based hashCode changes identity mid-transaction. Use a business key, or a constant hash with a real equals, deliberately.
    • Objects.hash(...) allocates a varargs array on every call. Fine almost everywhere; worth hand-writing the 31 * result + field form on a genuinely hot key class.

    Immutable classes

    ImmutableClass.java

    Five rules · and why final alone is not one of the answers

    • Immutable = once constructed, the state can never change. JDK examples: String, all the wrappers, LocalDate.
    • Why: safe to share freely, thread-safe with no locking, and safe as a HashMap key — the hash can never drift.

    The five rules

    • 1 — class is final, so nobody extends it and overrides a method to add mutation.
    • 2 — every field is private final, so nothing can be reassigned after the constructor.
    • 3 — no setters. At all.
    • 4 — every field is set inside the constructor.
    • 5 — if a field is itself a mutable object, defensive-copy it in the constructor and copy it again in the getter.
    final class Student {
    private final String  name;
    private final College college;                // mutable type → danger

    public Student(String name, College college){
        this.name = name;
        this.college = new College(college.getName(), college.getAddress());  // copy IN
    }
    public College getCollege(){
        return new College(college.getName(), college.getAddress());         // copy OUT
    }
}
    The two leaks — both are the same mistake
    • Constructor leak: this.college = college; stores the caller's own object. They keep their reference and call college.setName("IITB") later — your “immutable” object changed.
    • Getter leak: return this.college; hands your internal object out. Now anyone writes s1.getCollege().setName("IITD") and edits your field from outside.
    • final locks the arrow, not the box. private final College college only stops the reference being re-pointed — the object it points at is still fully editable.
    • String and primitive fields need no copy — String is already immutable, and primitives are copied by value anyway.
    • Encapsulation alone is not immutability. The College class here is properly private with getters and setters, and it is still mutable — a public setter is a mutation door however private the field behind it is.
    • A Java 14+ record gives you shallow immutability for free, but it still does not deep-copy a mutable component. Rule 5 survives records.
    One level down — why final fields are a memory-model guarantee

    final on a field is not only a compiler restriction. The Java Memory Model gives it a freeze action at the end of the constructor: any thread that sees a reference to the object is guaranteed to see its final fields fully initialised, with no synchronisation at all.

    Drop the final and that guarantee is gone. Another thread can legally observe a partially constructed object — the reference visible, the fields still at their defaults. This is why “immutable objects are thread-safe” is a real claim about the JMM, not a slogan.

    The guarantee has one condition: this must not escape the constructor. Register a listener or start a thread inside your constructor and you have published a half-built object before the freeze.

    In production — the shapes this actually takes
    • Arrays are always mutable, and private final byte[] data protects nothing. clone() it in and out, or expose it as a read-only view. Same for Date, Calendar, and any collection.
    • A defensive copy of a collection must be a real copy. Collections.unmodifiableList(list) is a view — the caller still holds the original and can mutate it through the back door. List.copyOf(list) (Java 10+) actually copies.
    • Copy in, then validate — in that order. Validating the caller's object and then copying leaves a window where a second thread edits it between the two steps: a time-of-check-to-time-of-use bug.
    • Prefer java.time. LocalDate and friends are immutable, which removes an entire class of copy obligations that java.util.Date forced on every DTO.
    Say it out loud

    Final class, private final fields, no setters, and defensive copies in and out for any mutable field.

    Nested classes

    NestedClasses/

    Four types · the outer.new Inner() syntax · when each is the right call

    • Two real reasons to nest. Logical grouping — if a class is only useful to one other class, keep it inside instead of loose in the package. And access — a nested class reaches the outer class's private members directly, with no getter, and the outer class can reach its private members back.
    • Static nested: new Outer.Inner() — no outer object needed, and therefore no access to the outer class's non-static members. To reach them, pass an Outer in as a parameter. Correct choice for a pure helper like InterestCalculator.
    • Inner (non-static): outer.new Inner() — needs an outer instance, and secretly holds a reference to it. That hidden reference is how it sees x directly — and also why it keeps the outer object alive in memory. Prefer static nested when you do not need the link.
    • Local class: declared inside a method body, visible only there, no access modifiers, and it may only use the method's local variables if they are final or effectively final.
    • Anonymous class: a local class with no name, declared and instantiated in one expression, usually to override one method once. Since Java 8, a lambda replaces it whenever the interface has exactly one abstract method.

Outer.Inner a = new Outer.Inner();

    Where objects actually live ★

    the JVM under every card above

    Stack, heap, metaspace — the model that makes call-by-value, the String pool and GC one topic

    • Stack — one per thread. Holds a frame per method call: local variables, the operand stack, and the return address. Popped automatically on return, so nothing here is ever garbage collected. Overflow it (unbounded recursion) and you get StackOverflowError.
    • Heap — shared by all threads. Every object and every array lives here, and this is the only region the garbage collector manages. Exhaust it and you get OutOfMemoryError: Java heap space.
    • Metaspace — class metadata. Class structures, method bytecode, the runtime constant pool. It replaced PermGen in Java 8 and grows into native memory rather than a fixed region, which is why PermGen space errors disappeared and class-loader leaks got quieter instead of louder.
    • The String pool lives in the heap (moved there in Java 7), so interned strings are collectable. Compact strings (Java 9+) store Latin-1 text in a byte[] rather than a char[], roughly halving the footprint of ordinary text.
    • Primitives are not automatically “on the stack”. A local primitive is a stack slot; a primitive field lives inside its object, on the heap. The distinction is local variable vs field, not primitive vs object.

    One level down — generational GC

    The heap is split because of one observation, the weak generational hypothesis: most objects die very young. So allocation happens in Eden, survivors are copied between two survivor spaces, and only objects that survive enough cycles are promoted to the old generation.

    That makes a minor GC cheap: it copies the few live objects out and declares the whole region free, so its cost is proportional to what survives, not to what was allocated. Allocation itself is a pointer bump in a thread-local buffer — genuinely a few instructions.

    The practical consequences: short-lived garbage is nearly free, so “avoid allocation” is usually premature; long-lived caches are what actually cost you, because they are promoted and then scanned by every major collection. And a memory leak in Java is not a missing free — it is an unintended strong reference. Static collections, listeners never deregistered, and ThreadLocals never removed in a pooled thread are the three that recur.

    Is String s = "abc" on the stack or the heap?

    The variable s is a stack slot in the current frame. The object it points at is on the heap, in the string pool region. Since Java 7 the pool is part of the normal heap, so an interned string can be garbage collected once nothing refers to it.

    The follow-up worth pre-empting: new String("abc") creates a second object outside the pool that merely shares the same character data. That is why == fails on it and .equals() does not.

    Say it out loud

    Stack per thread, heap shared, metaspace for classes. References are stack slots; the objects are always on the heap; only the heap is collected.

    Shallow vs deep copy

    the other half of ImmutableClass.java

    The follow-up to every defensive-copy answer

    • Shallow copy: a new object whose reference fields point at the same nested objects. Two wrappers, one set of contents — edit through either and both see it.
    • Deep copy: a new object whose reference fields point at fresh copies, recursively, all the way down.
    • Object.clone() is shallow, and it is a broken design: it is protected, it needs the marker interface Cloneable (which declares nothing), it throws a checked CloneNotSupportedException, and it bypasses constructors entirely — so final fields cannot be set and invariants are never checked.
    • Prefer a copy constructor or a static factory: new Student(other) or Student.copyOf(other). Ordinary code, no interface, no checked exception, works with final fields, and it can return a subtype.
    • new ArrayList<>(list), Arrays.copyOf and List.copyOf are all shallow. You get a new list; the elements are shared. That is usually correct — if the elements are immutable.
    // shallow — one College, two Students
Student b = new Student(a.name, a.college);
b.college.setName("IITB");     // a.college changed too

// deep — copy constructor all the way down
Student(Student other){
    this.name    = other.name;                    // String is immutable: share it
    this.college = new College(other.college);   // mutable: copy it
}
    In production
    • Depth is a decision, not a default. Copy exactly as deep as the mutable part goes and no further — deep-copying an immutable graph is pure waste, and a full deep copy of an object holding a connection or a cache is a bug.
    • Serialization round-tripping as a deep copy (write to bytes, read back) is a real technique and a slow one, and it silently drops anything transient. Reach for it only for genuinely arbitrary graphs.
    • Records give you a shallow copy for free and no more — the canonical constructor is the place to defensive-copy a mutable component, and it is the only place that will run for every construction path.
    • A cyclic graph breaks a naive recursive deep copy outright. Real deep-copy code needs an identity map of already-copied objects — which is one of the few honest uses for IdentityHashMap.
    Say it out loud

    Shallow copies the references, deep copies the objects behind them. clone() is shallow and best avoided — use a copy constructor.

    Wrappers & autoboxing ★

    Autoboxing/

    Boxing is free · the traps are not

    • Every primitive has a matching class in java.lang. Two names break the pattern: int → Integer and char → Character; the other six just capitalise.
    • Why wrappers exist: collections and generics hold objects only — ArrayList<int> is illegal. A wrapper can also be null, which is how you express “no value”. And they carry utilities: Integer.parseInt("25"), Integer.MAX_VALUE.
    • Autoboxing is primitive → wrapper, unboxing the reverse, both inserted silently by the compiler: Integer a = 10; becomes Integer.valueOf(10), and int b = a; becomes a.intValue().

    Three more traps
    • Unboxing a null wrapper throws NullPointerException — the classic Integer x = map.get(k); int y = x; compiles perfectly and dies at runtime.
    • list.remove(1) on a List<Integer> removes index 1; list.remove(Integer.valueOf(1)) removes the value 1. The overload resolution picks the primitive version.
    • Boxing in a hot loop allocates on every iteration — Long sum = 0L; over a million iterations boxes a million times. Use the primitive type for the accumulator.
    One level down — the cache is configurable, and that matters

    Integer.IntegerCache is a static array built at class-initialisation time. The lower bound is fixed at −128; the upper bound is tunable with -XX:AutoBoxCacheMax=<n>. So the exact value at which == starts failing is a JVM flag, not a language rule — which is the real reason never to rely on it.

    The other wrappers differ: Boolean, Byte, Short, Character and Long cache a fixed range and cannot be tuned. Float and Double cache nothing at all — Double a = 1.0, b = 1.0; a == b; is always false.

    The constructors (new Integer(5)) have been deprecated for removal since Java 9 precisely because they defeat the cache and guarantee an allocation. valueOf() is the only right call, and autoboxing already emits it.

    In production — boxing is where the allocations hide
    • A Map<Integer, Integer> with a million entries costs several times what an int[] or a primitive-specialised map does: every key and value is a separate 16-byte object plus a reference. This is the single most common cause of surprising heap growth in data-heavy Java.
    • Mixed-type comparison is the silent one. Long.valueOf(1).equals(Integer.valueOf(1)) is false — equals checks the class first. Reading an int id from one source and a long from another produces a lookup that always misses, with no error anywhere.
    • The ternary operator unboxes. Integer x = flag ? null : 0; throws a NullPointerException, because mixing Integer and int branches forces the whole expression to int. It looks like a null assignment and is not.
    • In a loop, sum += i on a boxed accumulator allocates once per iteration. Streams have IntStream/LongStream for exactly this reason.
    Say it out loud

    Wrappers are objects, so == compares references. valueOf() caches −128 to 127, which is why the bug hides on small numbers.

    Generics

    typecasting/Demo1.java

    Compile-time type safety · erasure · the wildcard question

    • The point of generics is moving a cast from runtime to compile time. A raw List hands you Object and you cast — and find out about the mistake when it crashes. List<String> refuses to compile instead.
    • A type parameter is just a placeholder: class Box<T>. Convention: T type, E element, K/V key and value, N number.
    • Type erasure: generics exist only at compile time. After compiling, Box<String> and Box<Integer> are the same class — the type is erased to Object (or to the bound) and casts are inserted for you.
    • Erasure explains the restrictions: no primitives (Box<int> is illegal — hence wrappers), no new T(), no generic arrays, and instanceof Box<String> is meaningless.
    • Bounded: <T extends Number> restricts what T can be and lets you call Number's methods on it.
    class Box<T> {
    private T value;
    Box(T value){ this.value = value; }
    public T getValue(){ return value; }
}

Box<String> b = new Box<>("Hello world");
String s = b.getValue();     // no cast, checked at compile time
    Why is List<Object> not a supertype of List<String>?

    Because it would break type safety. If List<String> could be assigned to a List<Object> variable, you could then add(42) through it and the original list would be holding an Integer where every reader expects a String.

    Generics are invariant for exactly that reason. Wildcards restore the flexibility safely: List<? extends Number> you can read from (producer), List<? super Integer> you can write to (consumer) — the PECS rule: producer extends, consumer super.

    One level down — what erasure leaves behind

    Erasure is not quite “the types vanish”. Two artefacts survive and both show up in real work:

    • Bridge methods. Implement Comparable<Student> and you write compareTo(Student), but the interface after erasure demands compareTo(Object). The compiler synthesises a second method that casts and delegates. It is why a stack trace can name a method you never wrote, and why a ClassCastException can be thrown from a line that contains no cast.
    • Signatures in the class file. Generic types are kept in a Signature attribute for the compiler and for reflection — which is how getGenericSuperclass() works, and how the “super type token” trick (new TypeReference<List<String>>(){}) recovers a type argument at runtime. Jackson and Spring both rely on it.

    Heap pollution is the other consequence: because the runtime cannot check the type argument, an unchecked cast can put a String into a List<Integer>, and the failure surfaces later at an implicit cast in unrelated code. That is what @SafeVarargs and the “unchecked” warning are about — the compiler telling you it can no longer help.

    Design note — PECS in one working example 
    void copy(List<? extends T> src, List<? super T> dst){   // producer / consumer
    for (T t : src) dst.add(t);
}
// src PRODUCES T  → ? extends T  → you may read T, never add
// dst CONSUMES T  → ? super T    → you may add T, reads give Object

    The rule people miss: a List<? extends Number> is not a “list of some subtype of Number” you can write to — the compiler does not know which subtype, so every add is rejected except null. That refusal is the type system doing its job, not an inconvenience to cast around.

    Type casting

    typecasting/Demo.java

    Primitives widen silently · objects need instanceof

    • Widening (implicit): small type into big type, done automatically, no data loss. byte → short → int → long → float → double, and char → int.
    • Narrowing (explicit): big into small needs a cast and can silently lose data — (byte) 130 gives you -126, no warning, no exception.
    • Upcasting a reference (Parent p = new Child();) is implicit and always safe. Downcasting (Child c = (Child) p;) is explicit and throws ClassCastException if the object is not really a Child.
    • Guard every downcast: if (p instanceof Child c) { ... } — Java 16+ pattern matching does the check and the cast in one step.

    • (int) 9.99 truncates toward zero — it does not round. Use Math.round() when you meant rounding.
    • int / int is integer division: 5 / 2 is 2, not 2.5. Cast one operand first.

    String, the pool & the builders

    Strings/Demo.java

    Immutable · literal vs new · the three classes and when each one wins

    One level down — what the compiler and JVM do for you

    • hashCode() is cached in a field, computed lazily on first call. That is a direct consequence of immutability — and it is why String is the ideal HashMap key.

    • Never build SQL or HTML with +. The immutability discussion is the wrong reason to avoid it; injection is the right one. Parameterised statements, always.
    • intern() is a sharp tool. It can collapse millions of duplicate strings from a parser into one each — and it can also add a native-table bottleneck. Measure; do not sprinkle.
    • equalsIgnoreCase and toLowerCase() are locale-sensitive. In a Turkish locale "I".toLowerCase() is not "i", and identifier comparisons start failing on one customer's machine only. Use toLowerCase(Locale.ROOT) for anything that is not user-facing text.

    enum

    Enum/

    A class in disguise · type safety that int constants never had

    • An enum is a class that implicitly extends java.lang.Enum — which is why it cannot extend anything else. It can implement interfaces.
    • Every constant is a public static final instance of that enum type, created once. The constructor is implicitly private — you can never new an enum.
    • You get for free: values() (all constants, in declaration order), ordinal() (zero-based position), name(), valueOf(String), and correct equals/hashCode/compareTo.
    • The real benefit is type safety. A method taking Direction can only ever receive one of four values; a method taking int accepts -7 and finds out later.
    • Enums can carry fields, constructors and methods, and each constant can even override a method — the constant-specific body, which is the clean replacement for a switch over types.
    enum Direction {
    NORTH("up"), SOUTH("down"), EAST("right"), WEST("left");

    private final String label;              // enums can hold state
    Direction(String label){ this.label = label; }   // constructor is implicitly private
    public String move(){ return "Moving " + label; }
}

for (Direction d : Direction.values())
    System.out.println(d + " " + d.ordinal() + " " + d.move());
    The traps
    • Never persist ordinal() to a database or file — reordering the constants silently changes every stored value. Store name().
    • valueOf("north") is case-sensitive and throws IllegalArgumentException, not null.
    • Compare enums with == — it is safe here (single instances) and null-safe, unlike equals on a null reference.

    Checked vs unchecked exceptions

    JavaI/o/revision.txt

    The boundary your notes actually reach — and it is enough to answer the I/O question

    • Checked exceptions are verified by the compiler. If a method can throw one, you must either catch it or declare throws. IOException, SQLException, FileNotFoundException.
    • Unchecked exceptions extend RuntimeException and need neither. NullPointerException, ArithmeticException, ArrayIndexOutOfBoundsException, ClassCastException, NumberFormatException.
    • The design intent: checked = a failure the caller could reasonably recover from (the file is missing, the network dropped). Unchecked = a programming bug that should be fixed, not caught.
    • That is why br.readLine() forces throws IOException on main: the stream really can fail for reasons outside your code.
    • Error (OutOfMemoryError, StackOverflowError) is a third branch — unchecked, and not meant to be caught at all.

    Exception handling, properly ★

    the depth behind card 07

    finally, resources, suppression — and the four ways teams get this wrong

    • throw vs throws: throw is a statement that raises one exception object now; throws is a clause on a signature declaring what may escape. One verb, one contract.
    • finally almost always runs — after a return, after a throw, on every path. The exceptions: System.exit(), a JVM crash, or the thread being killed.
    • A return inside finally discards the pending exception and silently replaces the returned value. It compiles, it produces no warning, and it deletes the failure entirely. Never return from finally.
    • Multi-catch catch (IOException | SQLException e) requires the types to be unrelated, and e is effectively final inside the block.
    • Catch order is most-specific first. Putting catch (Exception e) above catch (IOException e) is a compile error — unreachable code — which is the one time the compiler protects you here.

    try-with-resources, and what it added

    try (BufferedReader br = new BufferedReader(new FileReader(f))) {
    return br.readLine();
}   // close() is called automatically, in REVERSE order of declaration,
    // before any catch or finally block runs
    • Any AutoCloseable works. Resources close in reverse declaration order, so the outer wrapper closes before the stream it wraps.
    • It fixes a real bug in hand-written finally. If the body throws and then close() also throws, the old code lost the original exception. Try-with-resources keeps the body's exception as primary and attaches the close failure as a suppressed exception, readable via getSuppressed().
    One level down — how the JVM implements it

    There is no try instruction. The compiler emits an exception table for the method: rows of { start pc, end pc, handler pc, caught type }. On a throw, the JVM walks that table for the current frame; no match, and it pops the frame and repeats up the stack.

    That is why entering a try block costs nothing — there is no runtime setup at all. The cost is entirely in throwing, and almost all of that is fillInStackTrace() walking the stack. An exception used for control flow in a hot loop is orders of magnitude slower than an if; the same exception with the stack trace suppressed is cheap.

    finally is not a JVM construct either — the compiler duplicates the finally block into every exit path, plus a catch-all handler that rethrows. That duplication is exactly why a return inside it can swallow the in-flight exception.

    In production — the four failures worth naming
    • Swallowing. catch (Exception e) { }, or logging without rethrowing on a path that cannot continue. The system carries on with corrupt state and the real failure surfaces somewhere unrelated, hours later.
    • Losing the cause. throw new ServiceException("failed") without passing e. Always new ServiceException(msg, e) — the chained cause is the entire value of the stack trace.
    • Catching too wide. catch (Exception) also catches RuntimeException, so a NullPointerException in your own code gets reported as “the remote call failed”.
    • Catching Throwable. Now you have caught OutOfMemoryError and are attempting recovery inside a JVM that cannot allocate. Let Errors kill the process.

    Custom exceptions: extend RuntimeException unless the caller can genuinely do something different because of this specific failure — that is the whole test for checked vs unchecked in your own code. Carry the data the handler needs as fields (an order id, an error code), not buried in a formatted message string.

    Say it out loud

    Catch what you can handle, wrap the rest with the cause attached, close with try-with-resources, and never return from finally.

    Functional interfaces & lambdas ★

    Comparable/note.txt · NestedClasses/

    Your own Comparable note already lands on this — one abstract method is the whole rule

    • A functional interface is any interface with exactly one abstract method. Default, static and private methods do not count, and neither do public methods inherited from Object — which is why Comparator can declare equals and stay functional.
    • @FunctionalInterface is optional and worth writing: it makes “someone added a second abstract method” a compile error in this file rather than a mystery at every call site.
    • A lambda is not sugar for an anonymous class. An anonymous class produces a real Outer$1.class file and a new instance per evaluation. A lambda compiles to a private static method plus an invokedynamic call site that LambdaMetafactory links on first use.
    • A non-capturing lambda is a singleton — the same instance is reused for every evaluation. A capturing one allocates per call. That is the concrete reason to prefer x -> x.getName() over a lambda that closes over a local.
    • this inside a lambda is the enclosing instance. Inside an anonymous class it is the anonymous instance. That difference alone breaks naive conversions between the two.

    One level down — effectively final, and why

    A lambda may capture a local only if it is final or effectively final (never reassigned). The reason is the memory model, not tidiness: locals live in a stack frame that disappears when the method returns, so the captured value is copied into the lambda. If reassignment were allowed there would be two independent copies and no defined answer for which one you see — the same reasoning as pass-by-value in card 03.

    Instance and static fields have no such rule, because those are captured as this plus a field read — a live reference, not a copy. That is also the trap: a lambda stored in a long-lived listener list captures the enclosing instance and keeps it alive. It is the modern shape of the inner-class memory leak.

    One abstract method makes an interface functional, and a lambda is an implementation of that one method — linked by invokedynamic, not compiled into an extra class file.

    The bug hiding inside your lambda
    • s1.marks - s2.marks is a subtraction comparator, and subtraction of int overflows. With marks of 85 and 88 it is fine forever; the moment the same habit reaches a timestamp, an id or anything that can go negative, 2000000000 - (-2000000000) wraps to a negative number and the sort quietly produces the wrong order.
    • Since Java 7 the sort is TimSort, which validates its own assumptions while merging runs. An inconsistent comparator then throws IllegalArgumentException: Comparison method violates its general contract — but only once the list is large enough to trigger a merge, which is why it never appears on a three-element demo and always appears in production.
    • The fix is one word: Integer.compare(s1.marks, s2.marks), or let Comparator.comparingInt do it. Never -, and never a.marks > b.marks ? 1 : -1 either — that one never returns 0, so equal elements are reported as unequal and stability is lost.
    • The same trap eats doubles: subtracting two doubles and returning it as an int truncates 0.4 to 0, so near-equal values compare equal. Use Double.compare.
    One level down — what Collections.sort actually does with your lambda

    Collections.sort(list, c) has been a one-line delegation to list.sort(c) since Java 8, and ArrayList.sort does three things: sort the backing elementData array in place with Arrays.sort(a, 0, size, c), bump modCount, and check it afterwards — so mutating the list from inside your comparator throws ConcurrentModificationException.

    Arrays.sort with a comparator is TimSort: a stable, adaptive merge sort that finds already-ordered runs, extends short ones by binary insertion, then merges. Stability matters here — it is the reason thenComparing works at all, and the reason sorting by name and then by marks yields “by marks, ties broken by name”. Primitive arrays get a different algorithm (dual-pivot quicksort, not stable) because identical ints have no identity to preserve.

    Your comparator is called O(n log n) times, so it must be cheap and pure. A comparator that hits a database, allocates, or reads mutable state is a performance bug and a correctness bug at the same time.

    Method references, all four kinds ★

    Lambda/note.txt

    Your note lists them — this is the version that compiles, plus the rule for telling them apart

    • A method reference is a lambda whose entire body is one call, with the arguments passed straight through. That is the whole test. x -> Math.abs(x) passes x through untouched, so it collapses. x -> Math.abs(x) + 1 does not.
    • It is ::, two colons, and there is never an argument list. String::isEmpty is a reference; String::isEmpty() does not compile, because the parentheses would mean you are calling it now.
    • The same reference can become different interfaces. String::isEmpty is a Predicate<String> in filter and a Function<String,Boolean> elsewhere.     • They are not limited to JDK methods. Student::getMarks, this::validate and MyUtils::clean all work. The only requirement is that the signature lines up with the functional interface.

    Functional composition

    Lambda/note.txt · the last two lines

    “Break the code into multiple functions and then andThen()” — this is what that buys you

    • Composition is how small functions become one function without anybody writing glue. Each built-in functional interface carries default methods that return a new instance of the same interface, so the result can be composed again. The chain is a value you can name, store and pass around.
    • Nothing runs while you compose. f.andThen(g).andThen(h) allocates wrappers and calls none of them. Execution happens on apply — the same lazy shape streams are built on, which is why this card is the door into filter / map / collect.
    • andThen reads left to right; compose reads right to left. f.andThen(g).apply(x) is g(f(x)). f.compose(g).apply(x) is f(g(x)). If you remember only one, remember andThen and never write compose.
    • Predicate composes with and, or, negate, and they short-circuit exactly like && and || — so put the cheap test first.
    • Comparator is the composition you already use: comparing → thenComparing → reversed, which replaces your three SortBy… classes with a single expression.

    The three composition traps
    • reversed() reverses the whole chain built so far, not the last key. comparing(A).thenComparing(B).reversed() reverses both keys. To reverse only B: comparing(A).thenComparing(B, Comparator.reverseOrder()). This is the most common comparator bug after subtraction.
    • compose runs its argument first. Reading f.compose(g) left to right gives the wrong order and a silent bug — the code still compiles, because both sides are Function. Prefer andThen; it is the same operation written in the order it executes.
    • A composed comparator is still called O(n log n) times. comparing(s -> expensive(s)) recomputes the key on every comparison, not once per element. If the key costs anything, compute it into a field first — or accept paying for it roughly 2n log n times.
    One level down — default methods are what made all of this possible

    Every composer above is a default method on an interface. Default methods exist so interfaces can evolve; lambdas are what made the new methods worth adding.

    This is also why default methods do not break the “one abstract method” rule from card 09: Comparator declares a dozen methods and stays functional because only compare is abstract.

    The one collision rule worth carrying: if a class inherits the same default method from two interfaces it must override it, and inside that override InterfaceName.super.method() picks a side. A class method always wins over any inherited default.

Streams are course #39–42 and still the largest gap in the repo; every functional interface they need is already on this page.

    HashMap internals ★

    set/note1.txt

    The highest-frequency question in the entire interview

    • The table is a Node[] array of buckets, and a node is { K key; V value; int hash; Node next; } — the next pointer is what makes each bucket a linked list.
    • Put, in four steps: hash the key → convert hash to a bucket index → if the bucket is empty, store a new node → if not, walk the chain.
    • Walking the chain compares hash first, then equals() — never the reference. Hash first because it is an int comparison and rules out most candidates instantly.
    • Duplicate key (hash and equals both match): no new node. The value is overwritten and the old value is returned. That returned value is precisely what makes set.add() return false.
    • New key: the node is appended at the end of that bucket's list. get() and containsKey() walk the exact same path.

    The equals / hashCode contract

    • If k1.equals(k2) is true, then k1.hashCode() == k2.hashCode() must be true.
    • The reverse is not true. Two different keys sharing a hash is just a collision — "Abhishek" and "Raj" both landing on 203 in the animation above are still two distinct entries.
    • So override equals() and you must override hashCode(), or the key is stored in one bucket and searched for in another and effectively disappears.
    • Collision strategy: Java uses chaining — a list per bucket. It does not use open addressing / linear probing, which is the other textbook technique.
    One level down — the three details the notes simplify
    • The index is a mask, not a modulo. index = (n - 1) & hash. That only distributes correctly when n is a power of two, which is why capacity is always rounded up to one — new HashMap<>(10) gives you 16. A modulo would work for any size but costs a division per lookup.
    • The hash is spread first: h ^ (h >>> 16). Because the mask keeps only the low bits, two keys differing solely in their high bits would collide in every bucket. XOR-ing the high half down mixes that information into the low bits for one shift and one XOR.
    • Insertion moved to the tail in Java 8. Java 7 prepended, which under concurrent resize could produce a circular chain — the notorious 100% CPU spin in get() on an unsynchronised HashMap. Tail insertion plus the Java 8 resize (which preserves relative order while splitting each chain into a low and a high list) removed that specific failure. An unsynchronised HashMap shared across threads is still broken — just differently.

    null keys are legal and are special-cased to bucket 0, since you cannot call hashCode() on null. ConcurrentHashMap forbids them, because a null return could not be distinguished from “absent” in a racy read.

    In production — the methods worth reaching for 
    map.computeIfAbsent(key, k -> new ArrayList<>()).add(value);   // one lookup, not three
map.merge(word, 1, Integer::sum);                              // the whole word-count idiom
map.getOrDefault(key, 0)                                       // no null check
    • Never mutate a key after insertion. The entry stays in its old bucket while every lookup goes to the new one: the value is unreachable, un-removable, and still holding memory.
    • Iteration order is not insertion order and is not stable across runs. Depending on it produces a test that passes locally and fails in CI. Use LinkedHashMap when order is part of the contract.
    • Attacker-controlled keys were once a denial-of-service vector — deliberately colliding strings turned a lookup into O(n). Treeification is what defanged it, which is a better answer to “why treeify?” than “performance”.
    Say it out loud

    Hash the key, mask to a bucket, walk the chain comparing hash then equals. A duplicate updates in place and returns the old value; everything else appends.

    Rehashing & treeification ★

    set/note1.txt

    “What changed in HashMap in Java 8?” — this card is the answer

    • Load factor = size / capacity, and the default is 0.75. Default initial capacity is 16.
    • Once size > capacity × 0.75, the table doubles (16 → 32 → 64 → 128) and every entry is re-indexed against the new capacity. That is rehashing.
    • Why bother: a small table means long chains, and a long chain turns O(1) lookup into O(n). Rehashing spreads the entries out again.
    • Why 0.75 specifically: it is the compromise. Lower wastes memory, higher lets chains grow before the resize triggers.
    • Sizing the map up front — new HashMap<>(1000) — avoids repeated resize-and-copy. That is a real performance answer, not trivia.
    ConstantValueWhat it triggers
    Initial capacity16size of the bucket array on first put
    Load factor0.75resize when size exceeds 12 of 16

    Untreeify threshold6tree degrades back to a chain

    One level down — why these exact numbers
    • 0.75 is a Poisson calculation, not a guess. With a good hash and load factor 0.75, the number of keys per bucket follows a Poisson distribution with mean 0.5. The probability of a bucket reaching 8 entries is about 0.00000006 — six in a hundred million. That is why 8 was chosen as the treeify threshold: under a sane hashCode() it should essentially never fire, so trees only appear when the hash is genuinely bad or adversarial.
    • 6 for untreeify, not 8, so a bucket hovering at the boundary does not convert back and forth on every put and remove. The gap is hysteresis.
    • The 64-entry minimum matters. Below it, a long chain means the table is too small, not that the hash is bad — so Java resizes instead, which is cheaper and fixes the actual cause.
    • Treeified buckets need ordering. If the keys are Comparable the tree uses that; otherwise it falls back to comparing class names and identity hash codes to break ties. A tree still works with non-comparable keys, just less efficiently.
    In production — sizing, correctly

    The constructor argument is the capacity, not the number of entries you plan to store. new HashMap<>(1000) rounds to 1024 and then resizes at 768 — before you have stored your thousand entries.

    new HashMap<>((int)(expected / 0.75f) + 1);   // pre-Java 19
HashMap.newHashMap(expected);                 // Java 19+, does the arithmetic for you

    A resize is not just an allocation: it re-links every entry in the table. Doing that repeatedly while loading a large map is a startup cost that profiles clearly and disappears with one constructor argument.

    Say it out loud

    Load factor 0.75 triggers a double-and-reindex. A chain of 8 triggers treeification to a red-black tree — so Java 8 moved the worst case from O(n) to O(log n).

    LinkedHashSet & TreeSet

    set/Demo1.java · set/Demo2.java

    Order costs something — know what you are paying

    • HashSet has no order at all. Iteration follows bucket order, which is a function of hash values, not of insertion. Never rely on it — small integers can look sorted by coincidence.
    • LinkedHashSet = hash table + doubly linked list. Each node gains before and after pointers threading every entry in insertion order. You keep O(1) lookup and pay a little extra memory.
    • TreeSet is not hashing at all. It is a red-black tree — a self-balancing BST, smaller left, larger right. Everything is O(log n), and iteration comes out sorted.
    • TreeSet needs to compare, so its elements must be Comparable or you must supply a Comparator — and it allows no nulls. HashSet and LinkedHashSet each allow one.
    • For Strings, TreeSet's natural order is lexicographic — and uppercase sorts before lowercase, because it is really comparing char codes.

    Hashtable vs ConcurrentHashMap — why is one slow?

    Hashtable synchronizes the whole map on every method. Two threads reading different buckets still queue behind one lock, so throughput collapses as threads are added.

    Why does ConcurrentHashMap forbid null keys and null values?

    Because of the ambiguity in fact two, made unfixable by concurrency. In a HashMap, get(k) == null can be disambiguated with containsKey(k). In a concurrent map another thread can insert or remove between those two calls, so the pair of calls proves nothing — and there is no atomic way to ask both questions at once.

    The designers’ answer was to remove the ambiguity at the source: no nulls, so null from get means exactly one thing. Hashtable does the same. Plain HashMap allows one null key — special-cased into bucket 0, since null.hashCode() cannot be called — and any number of null values. TreeMap allows no null key at all, because it must call compareTo on it.

    Why is Map.of() not just a shorter HashMap?

    Three real differences. It is immutable — every mutator throws UnsupportedOperationException, so it is safe to return from a getter with no defensive copy. It rejects nulls in keys and values, at construction. And its iteration order is deliberately randomised per JVM run, so code that accidentally depends on the order fails in testing rather than in production.

    Map.of takes up to ten pairs; beyond that use Map.ofEntries(Map.entry(k, v), …). Map.copyOf(existing) takes a real copy — unlike Collections.unmodifiableMap, which is only a read-only view that still changes when whoever holds the original mutates it.

    Queue, Deque & ArrayDeque

    Queue/Note.txt · Queue/Demo1.java

    FIFO, the circular array trick, and why Stack is the wrong class

    • Queue is FIFO — first in, first out. Deque (double-ended queue) extends it so you can add and remove at both ends, which is how it doubles as a stack.
    • Hierarchy: Iterable → Collection → Queue → Deque, implemented by ArrayDeque and LinkedList.
    • LinkedList hangs off two branches at once — it implements List and Deque, which is the pair circled in Queue/implements.png. That is why the same object can be indexed like a list and polled like a queue, and why Deque<Integer> d = new LinkedList<>() and List<Integer> l = new LinkedList<>() both compile. ArrayDeque implements only Deque — no get(i), by design.
    • Array implementation: two pointers, front and rear, both starting at −1. Adding moves rear forward, removing moves front forward. Both wrap around — a circular array — so the freed slots at the front get reused instead of wasted.
    • Full is when (rear + 1) % n == front. Then you allocate a bigger array and copy everything across, exactly like ArrayList growth.
    • Linked-list implementation: front and rear node pointers; add and remove are O(1) with no resize ever — but every element costs an extra node object and its pointers.

    ArrayDeque or LinkedList — and why not Stack?

    By the shape of the code, LinkedList looks better — O(1) at both ends, no resizing. The javadoc still recommends ArrayDeque, and the reason is memory layout: an array is contiguous and cache-friendly, while a linked list scatters nodes across the heap and pays a pointer-chase on every step. The occasional resize costs less than the cache misses.

    The trade-off: ArrayDeque does not allow null (null is its “empty” signal), LinkedList does.

    And Stack is a legacy class — it extends Vector, so every method is synchronized and you pay for locking you never asked for. It also exposes get(i), which breaks the whole point of a stack. Use ArrayDeque with push / pop / peek instead.

    // a stack, done properly
Deque<Integer> stack = new ArrayDeque<>();
stack.push(10); stack.push(20);
stack.pop();     // 20 — LIFO

// a queue, same class
Queue<Integer> q = new ArrayDeque<>();
q.offer(10); q.offer(20);
q.poll();        // 10 — FIFO
    One level down — ArrayDeque's real indices

    The front = rear = -1 model is the right way to think, but the JDK uses head and tail starting at 0, with emptiness expressed as head == tail. The array length is always a power of two, so the wrap is a bitmask rather than a modulo:

    head = (head + 1) & (elements.length - 1);   // same as % length, one instruction

    That is the identical trick HashMap uses for bucket indices — worth naming as one idea rather than two facts. When full it doubles and copies, so amortised O(1), exactly like ArrayList.

    The rest of the Queue family — what interviewers add next
    • PriorityQueue implements Queue but is not FIFO: it is a binary heap in an array, poll() returns the smallest, offer and poll are O(log n), peek is O(1). Its iteration order is heap order, not sorted — only repeated poll() comes out in order, and that surprises people in a code review.
    • BlockingQueue is the producer-consumer answer: put() blocks when full, take() blocks when empty, so the two sides need no locks of their own. ArrayBlockingQueue is bounded, LinkedBlockingQueue optionally so — and bounded is the safer default, because an unbounded queue in front of a slow consumer is a memory leak with a queue's name on it.
    • ConcurrentLinkedQueue is the lock-free, non-blocking option. Note that its size() is O(n) and only approximate — do not poll it in a loop.
    • None of ArrayDeque, LinkedList or PriorityQueue is thread-safe.

    Iterable & Iterator ★

    Interable/Iterable_Notes.md

    One traversal interface for structures that share nothing internally

    • The problem it solves: an array is a contiguous block, a LinkedList is nodes chained by next, a HashSet is buckets with no index at all. Without a common interface you would need a different loop for each.
    • Iterable means “I can hand out a cursor” — one method, iterator(). Iterator is the cursor: hasNext(), next(), and optionally remove().
    • next() does two things: returns the current element and advances the pointer. Calling it twice in one loop iteration silently skips elements and ends in NoSuchElementException.
    • The position lives in the iterator, not in the collection. That is the whole design — two calls to iterator() give two independent cursors, so nested loops over the same collection work. Put pos in the collection instead and the inner loop consumes the outer one's position.
    • A for-each loop is an iterator loop; the compiler rewrites it. So for-each only works on something that implements Iterable.
    • Arrays are not Iterable — arr.iterator() does not exist. For-each still works on them because the compiler emits a plain index loop instead. Maps are not Iterable either; you iterate entrySet(), keySet() or values(), which are Collections.
    // what you write
for (String name : container) { ... }

// what the compiler builds
Iterator<String> it = container.iterator();
while (it.hasNext()) { String name = it.next(); ... }
    class NameContainer implements Iterable<String> {
    private String[] names;

    @Override public Iterator<String> iterator(){
        return new NameIterator();      // a FRESH cursor every call, pos = 0
    }
    private class NameIterator implements Iterator<String> {
        private int pos = 0;            // the state lives HERE, not in the container
        public boolean hasNext(){ return pos < names.length; }
        public String  next(){
            if (!hasNext()) throw new NoSuchElementException();
            return names[pos++];
        }
    }
}

    Iterable is the thing you can walk; Iterator is the walker. The position belongs to the walker, which is why one collection can hand out many independent cursors.

    Three bugs in four lines — and every one of them is an interview question

    // the buggy loop, exactly as written
Iterator<Integer> it = list.iterator();

    int value = it.next();
    if (value == 30) list.remove(value);       // bug 2 and bug 3

    • Bug 1 — next() twice in one iteration. Every loop pass consumes two elements, so half the list is skipped and the last pass throws NoSuchElementException.
    • Bug 2 — modifying the list inside the loop. ArrayList keeps a modCount of structural changes. iterator() copies it into expectedModCount; every next() checks modCount != expectedModCount and throws ConcurrentModificationException if they diverged. That is fail-fast: crash immediately rather than return a quietly wrong answer.
    • Bug 3 — the wrong remove overload. List<Integer> has both remove(int index) and remove(Object o). A primitive int picks the index version, so list.remove(30) tries to delete index 30 and throws IndexOutOfBoundsException. To remove the value: list.remove(Integer.valueOf(30)).

// 2. removeIf() — Java 8, shortest

    Comparable vs Comparator ★

    Comparable/Demo.java · Comparable/note.txt

    Your note gets the reason exactly right: Java has no idea how to order your class

    • The problem, as your note puts it: Java can order Strings lexicographically and numbers naturally, but given two Student objects it has no rule. Collections.sort(list) will not even compile, and a TreeSet of them throws ClassCastException at the first insert — because internally it is a BST and a BST must compare.

    The traps
    • Subtraction overflows. a.marks - b.marks is fine for exam marks and wrong for anything that can be large or negative — Integer.MIN_VALUE - 1 wraps to a positive number and the sort silently produces garbage.     Views, immutability & the gotcha list

    the things that bite after the interview

    Half the collections API returns a window onto something else, not a copy

    • A view shares storage with its source. subList, keySet, values, entrySet, Arrays.asList, headSet/tailSet, and everything from Collections.unmodifiable* are all views. Writes propagate; structural changes to the source invalidate the view.
    • Collections.unmodifiableList(x) is not immutable — it is an unmodifiable wrapper. Whoever still holds x can change it and the “unmodifiable” list changes underneath its readers.
    • List.of(...) and List.copyOf(x) are genuinely immutable (Java 9/10+): a real copy, rejecting nulls, and throwing UnsupportedOperationException on every mutator.
    • Arrays.asList is fixed-size and writes through to the array you passed — set works, add and remove throw.
    • The whole family throws UnsupportedOperationException rather than failing to compile, because they implement the same List interface. Immutability here is a runtime property, not a type.

    In production — the rest of the gotcha list
    • Never return your internal collection from a getter. It is the getter leak from the immutability card, at collection scale. Return List.copyOf(items) or an unmodifiable view of a field nobody else can reach.
    • Map.Entry objects from iteration are transient. Copy the key and value out if you need them after the loop.
    • Empty collection, not null. A method returning null instead of List.of() pushes a null check onto every caller forever. This is the single highest-value habit on this page.
    • Program to the interface — List<String> list = new ArrayList<>(), Map not HashMap. Your Deom.java already does this with Collection<Integer> list = new HashSet<>(), and it is why swapping the implementation later is a one-line change.
    • Synchronised wrappers do not make iteration safe. Collections.synchronizedList locks each method individually; iterating still requires you to hold the lock manually for the whole loop. Prefer ConcurrentHashMap and CopyOnWriteArrayList, which were designed for it.
    Say it out loud

    Most of the collections API hands back views, not copies — and “unmodifiable” means you cannot change it, not that it cannot change.

    Rapid-fire recall

    answer out loud first

    If an answer takes more than fifteen seconds, that card goes back into the notes

    Is Java pass by value or pass by reference?

    Always pass by value. For objects the reference value is copied, so mutating the object is visible outside but reassigning the parameter is not.

    Difference between overloading and overriding?

    Overloading: same name, different parameters, same class, resolved at compile time. Overriding: same signature, parent and child, resolved at runtime from the actual object.

    Why can't you override a static method?

    Because overriding is runtime dispatch on an object, and a static method belongs to the class. Redeclaring it in a child is method hiding, and it resolves by the reference type.

    Can an abstract class have a constructor?

    Yes — and it runs, via super(), when a concrete child is instantiated. You just cannot call new on the abstract class itself.

    Interface or abstract class — how do you choose?

    Shared state and code between related types → abstract class. A capability unrelated types can each claim → interface. A class has only one extends slot, so spend it carefully.

    What makes a class immutable?

    Final class, private final fields, no setters, all fields set in the constructor, and defensive copies in and out for any mutable field. final locks the reference, not the object it points at.

    Why must you override hashCode() when you override equals()?

    Because the contract says equal objects must have equal hash codes. Break it and a key is stored in one bucket and searched for in another — it vanishes from every HashMap and HashSet.

    Integer a = 127, b = 127; a == b; — true or false?

    true — valueOf() caches −128 to 127, so both refer to the same object. At 128 it is false. Always compare wrappers with .equals().

    What is type erasure?

    Generics exist only at compile time; the type argument is erased to Object (or the bound) in the bytecode. That is why there are no primitives as type arguments, no new T(), and no generic arrays.

    How does a HashMap store an entry?

    hashCode() → spread → index into the bucket array → if empty, store a node; if not, walk the chain comparing hash then equals(). Duplicate key overwrites and returns the old value; anything else is appended.

    What is the load factor, and what happens at it?

    0.75. Once size exceeds capacity × 0.75, the table doubles and every entry is re-indexed against the new capacity — rehashing.

    What changed in HashMap in Java 8?

    Treeification. A bucket chain reaching 8 nodes (with the table at least 64) becomes a red-black tree, moving the worst case from O(n) to O(log n). It degrades back to a list at 6.

    Why is a Set said to be a HashMap?

    Because HashSet literally holds a HashMap and stores your element as the key, with a shared dummy PRESENT object as every value.

    HashSet vs LinkedHashSet vs TreeSet?

    No order, O(1) / insertion order via a doubly linked list, O(1) / sorted red-black tree, O(log n) with range queries and no nulls.

    Why does Map not extend Collection?

    A Collection stores single elements; a Map stores key-value pairs, so add(E) has no meaning. Map defines its own method set, and is not Iterable — you loop entrySet().

    Difference between Iterable and Iterator?

    Iterable is the collection that can be walked — one method, iterator(). Iterator is the cursor that does the walking and holds the position. One Iterable can hand out many independent Iterators.

    What causes ConcurrentModificationException?

    A structural change to the collection while an iterator is live: modCount no longer matches the iterator's expectedModCount, so next() fails fast. Fix with it.remove() or removeIf().

    Fail-fast vs fail-safe?

    Fail-fast (ArrayList, HashMap) throws CME immediately. Fail-safe (CopyOnWriteArrayList, ConcurrentHashMap) iterates a snapshot, never throws, but may show stale data.

    ArrayDeque or LinkedList for a queue?

    ArrayDeque — a contiguous, cache-friendly circular array beats pointer-chasing across the heap. It just does not accept null. And it replaces the legacy synchronized Stack too.

    Checked vs unchecked exception?

    Checked is verified by the compiler — catch it or declare throws (IOException). Unchecked extends RuntimeException and needs neither (NullPointerException). Checked = recoverable condition; unchecked = programming bug.

    The second round — the follow-ups

    Comparable or Comparator — which and why?

    Comparable is the type's single natural ordering, written inside the class. Comparator is an external ordering, and you can have many — including for classes you cannot modify. Both return negative / zero / positive, and compareTo should be consistent with equals or TreeSet and HashSet will disagree about duplicates.

    Why is a.marks - b.marks a bad comparator?

    It overflows. For large or negative values the subtraction wraps and the sign flips, so the sort silently produces a wrong order. Use Integer.compare(a, b). Since Java 7 a broken comparator can also throw “Comparison method violates its general contract” — but only on inputs big enough for TimSort to start merging.

    Why is capacity always a power of two in HashMap?

    So the bucket index can be (n-1) & hash — a bitmask instead of a division. That only distributes correctly for a power of two, and it is why the hash is first spread with h ^ (h >>> 16): the mask keeps only the low bits, so the high bits have to be mixed down. ArrayDeque uses the same trick for its circular indices.

    Why 8 for treeification, and why 6 to go back?

    With a decent hash and load factor 0.75, bucket sizes follow a Poisson distribution — the chance of reaching 8 is about six in a hundred million. So treeification should essentially never fire unless the hash is bad or adversarial. The gap down to 6 is hysteresis, so a bucket at the boundary does not convert back and forth on every operation.

    Where does the String pool live, and why does that matter?

    In the heap since Java 7 (it was in PermGen before), so interned strings can be garbage collected. Since Java 9, strings use a byte[] with a coder flag — compact strings — roughly halving the memory of Latin-1 text, which is significant because strings are often a quarter of a server heap.

    What does final guarantee beyond “cannot reassign”?

    A memory-model guarantee: final fields are frozen at the end of the constructor, so any thread seeing the reference sees them fully initialised, with no synchronisation. That is the real reason immutable objects are thread-safe. It holds only if this does not escape the constructor.

    Is fail-fast guaranteed?

    No — the javadoc says so explicitly. modCount is an unsynchronised int, so across threads the iterator may never observe the change. Treat CME as a debugging aid for single-threaded bugs, never as a concurrency mechanism. ConcurrentHashMap's iterator is a third thing: weakly consistent — never throws, may or may not show later writes.

    Anonymous class or lambda — are they the same thing?

    No. An anonymous class produces a real class file and a new instance per evaluation. A lambda compiles to a private method plus an invokedynamic call site linked by LambdaMetafactory, and a non-capturing lambda is reused as a singleton. Also this means the enclosing instance in a lambda, and the anonymous instance in an anonymous class.

    Why must a captured local be effectively final?

    Because the local lives in a stack frame that disappears when the method returns, so its value is copied into the lambda. Allowing reassignment would create two independent copies with no defined answer for which one you see — the same reasoning as pass-by-value. Fields have no such restriction because they are captured through this.

    What is wrong with Collections.unmodifiableList(x)?

    It is a read-only view, not an immutable copy. Whoever still holds x can mutate it and every reader of the “unmodifiable” list sees the change. List.copyOf(x) actually copies. Same distinction as the defensive-copy rule for immutable classes.

    Why should a method never return null for a collection?

    Because it pushes a null check onto every caller, forever, and one of them will forget. Return List.of(). The same instinct applies to Optional as a return type for a single value — and to never using Optional as a field or a parameter.

    What does try-with-resources add over finally?

    It closes in reverse declaration order, before any catch or finally runs, and it fixes a real bug: if the body throws and close() also throws, hand-written finally loses the original. Try-with-resources keeps the body's exception as primary and attaches the close failure as a suppressed exception.

    The third round — lambdas, references and the map surface

    Name the four kinds of method reference.

    Static (Math::abs), bound instance (System.out::println — the receiver is an object you already hold), unbound instance (String::isEmpty — the receiver arrives as the first argument) and constructor (ArrayList::new, String[]::new). “Predicate reference” is not a fifth kind — that is an unbound reference that happens to land in a Predicate slot.

    s -> s.isEmpty() becomes String::isEmpty — where did the parameter go?

    It became the receiver. In an unbound reference the left side is a type, so the functional interface’s first parameter is the object the method is invoked on. The same rule explains why String::compareTo, a one-argument method, satisfies the two-argument Comparator: compare(a,b) runs as a.compareTo(b).

    andThen or compose — which one runs first?

    f.andThen(g) is g(f(x)) — reading order. f.compose(g) is f(g(x)) — the argument runs first. They compile to the same type, so getting it backwards is a silent bug. Use andThen.

    What exactly does .reversed() reverse in a comparator chain?

    Everything built before it, not the last key. comparing(A).thenComparing(B).reversed() flips both. To reverse only the second key: comparing(A).thenComparing(B, Comparator.reverseOrder()).

    Why is containsKey O(1) but containsValue O(n)?

    A key is hashed straight to its bucket, so the lookup touches one bucket. A value has no hash and no index — the map must walk every bucket and every node in each chain. Needing containsValue often means you wanted a second map keyed the other way round.

    What does map.computeIfAbsent(k, x -> new ArrayList<>()).add(v) save you?

    Two extra hash lookups and a branch — it replaces containsKey + put + get with one operation, and the new list is allocated only when the key is genuinely new. Its sibling map.merge(k, 1, Integer::sum) is the same trick for counting. Do not modify the same map inside the function: since Java 9 that throws ConcurrentModificationException.

    Why can’t ConcurrentHashMap store null?

    Because get(k) == null would be ambiguous — absent, or present with a null value — and the usual fix, a follow-up containsKey, proves nothing when another thread can change the map between the two calls. Banning null removes the ambiguity at the source. HashMap allows one null key (special-cased to bucket 0) and any number of null values; TreeMap allows no null key because it must call compareTo on it.
