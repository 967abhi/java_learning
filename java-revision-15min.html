    01

    OOPs foundation

    80s

    Class · object · constructor · static · call by value

    • Class is the blueprint, object is the real entity. A class holds fields (state) and methods (behaviour); it is not itself a thing in the world.
    • Constructor: same name as the class, no return type, runs automatically on new. Default, parameterised, copy.
    • Chaining uses this(...) or super(...) and must be the first statement. Overloading is not chaining — overloading is just same name, different parameter list, resolved at compile time.
    • static belongs to the class: one shared copy, accessed by class name, no this, cannot touch instance members directly. A static block runs once at class load — before main.
    • public static void main(String[] args) is the JVM's entry contract; args carries command-line input.
    Say it out loud

    Java is always pass by value. For objects the reference value is copied, so mutating the object is visible outside — but reassigning the parameter is not.

    02

    Encapsulation & access

    45s

    Data hiding · the real benefit · four modifiers

    • Binding data and the methods that act on it into one unit, then making the fields private with controlled getters and setters.
    • The real benefit is validation inside the setter — not the getter/setter ceremony itself. Without it anyone writes s.age = 500.
    • Getter only, no setter → a read-only field.
    • The compile error you get when you touch a private field from outside is the proof encapsulation works.
    ModifierSame classSame packageSubclass, other packageAnywhere
    privateyes———
    defaultyesyes——
    protectedyesyesyes—
    publicyesyesyesyes
    Say it out loud

    Encapsulation is private data plus a public gate, and the gate is where the rules live.

    03

    Inheritance & polymorphism

    75s

    extends · overriding rules · upcasting

    • extends for reuse. Types: single, multilevel, hierarchical. No multiple inheritance of classes (the diamond problem) — interfaces solve it.
    • Overloading = same name, different parameters, compile time. Overriding = same signature in parent and child, runtime.
    • Cannot override static (that is method hiding), private, or final. Access cannot be narrowed. Checked exceptions cannot be broadened.
    • super.method() reaches the parent version; super(...) calls the parent constructor and runs first, always.
    Say it out loud

    Methods are resolved at runtime by the object; fields and statics at compile time by the reference.

    05

    Immutable class

    45s

    The five rules — and the one everyone forgets

    final class Student {              // 1. final class - no subclass can add mutation
    private final String  name;      // 2. private final fields
    private final College college;   //    (this one is MUTABLE)

    Student(String name, College c) {
        this.name    = name;
        this.college = new College(c);  // 5a. defensive copy IN
    }
    College getCollege() {
        return new College(college);    // 5b. defensive copy OUT
    }                                  // 3. no setters  4. set in constructor
}
    • Why: safe to share, safe across threads with no locking, safe as a HashMap key (its hash can never drift).
    • From the JDK: String, all wrappers, LocalDate.
    The one everyone forgets
    • Returning the mutable field directly from the getter. The caller now holds a live handle and your object silently changes behind your back. Copy in, copy out.

    07

    Wrappers & autoboxing

    45s

    Boxing is free; the traps are not

    • Every primitive has a class in java.lang. Two odd names: int → Integer, char → Character.
    • Why they exist: collections and generics hold objects only, and a wrapper can be null where a primitive cannot.
    • Autoboxing primitive → wrapper, unboxing the reverse; the compiler inserts valueOf() / intValue() for you.
    Three more traps
    • Unboxing a null wrapper throws NullPointerException — the classic Integer x = map.get(k); int y = x;
    • list.remove(1) on a List<Integer> removes index 1; list.remove(Integer.valueOf(1)) removes the value.
    • Boxing in a hot loop allocates on every iteration — a real performance answer, not a trivia one.

    The collections family tree

    45s

    Draw this from memory — it is a whiteboard question

    Iterable
   └─ Collection
        ├─ List → ArrayList, LinkedList, Vector
        ├─ Set  → HashSet → LinkedHashSet
        │         └─ SortedSet → NavigableSet → TreeSet
        └─ Queue → Deque, PriorityQueue        ← still pending

Map (separate — NOT a Collection)
   ├─ HashMap → LinkedHashMap
   ├─ SortedMap → NavigableMap → TreeMap
   └─ Hashtable → Properties          (legacy branch)
    • Set declares almost no method of its own. It inherits from Collection and Iterable and only tightens the contract: no duplicates.
    • TreeSet is the exception — it gains real extra methods from SortedSet and NavigableSet.
    • Map is not a Collection, so it defines its own vocabulary: put get containsKey keySet values entrySet.
    • The pairing to remember: HashSet↔HashMap, LinkedHashSet↔LinkedHashMap, TreeSet↔TreeMap.
    09

    HashMap internals ★

    140s

    The single highest-frequency question in the whole interview

    • A Set is a HashMap wearing a disguise. HashSet holds a HashMap<K,Object>, and every value is the same dummy: private static final Object PRESENT = new Object();
    • set.add(x) → map.put(x, PRESENT). set.contains(x) → map.containsKey(x).
    class Node<K,V> { K key; V value; int hash; Node<K,V> next; }

boolean add(K key) { return map.put(key, PRESENT) == null; }
// put returns the OLD value: null means it was new  → true
//                            non-null means duplicate → false
    • get / containsKey walk the exact same path — hash, index, then chain-walk comparing hash and equals.
    • The contract: if k1.equals(k2) then k1.hashCode() == k2.hashCode() must hold. The reverse is not true — equal hashes are just a collision.
    • So: override equals() and you must override hashCode(), or your key goes into one bucket and gets looked up in another and vanishes.
    • Collision strategy: Java uses chaining (a linked list per bucket). It does not use open addressing / linear probing.
    Say it out loud

    Hash the key, mask to a bucket, walk the chain comparing hash then equals. Duplicate updates in place and returns the old value; everything else appends.

    10

    Rehashing & treeification ★

    80s

    "What changed in Java 8?" — this is the answer

    • Default capacity 16, load factor 0.75. Once size > capacity × 0.75, the table doubles and every entry is re-indexed against the new capacity.
    • Why bother: long chains turn O(1) lookup into O(n). Rehashing spreads entries back out.
    • Sizing a HashMap up front avoids repeated rehashing — a good performance answer.
    Say it out loud

    Load factor 0.75 triggers a double-and-reindex. A chain of 8 triggers treeification to a red-black tree, so the worst case went from O(n) to O(log n) in Java 8.

    11

    LinkedHashSet & TreeSet

    60s

    The "which one do you use" question

    • LinkedHashSet = the same hash table plus a doubly linked list threaded through every node (before / after), so iteration returns insertion order at no lookup cost.
    • TreeSet / TreeMap = no hashing at all. A self-balancing BST (red-black tree): smaller left, larger right. Everything is O(log n).
    • What TreeSet buys you: sorted iteration, first() / last(), ceiling floor higher lower, and range queries headSet tailSet subSet.
    • Strings sort lexicographically. Elements must be Comparable or you must supply a Comparator.

    13

    Iterable & Iterator ★

    80s

    Ends in ConcurrentModificationException — asked constantly

    • Iterable means "I can hand out a cursor" — one method, iterator(). Iterator is the cursor: hasNext(), next(), remove().
    • next() does two things: returns the current element and advances the pointer.
    • The state lives in the iterator, not the collection — two calls to iterator() give two independent cursors.
    • A for-each loop is an iterator loop; the compiler rewrites it. Arrays are not Iterable, but for-each still works on them because the compiler indexes instead.
    • Fail-fast (ArrayList, HashMap) throws CME. Fail-safe (CopyOnWriteArrayList, ConcurrentHashMap) iterates a snapshot and never throws.
    • ListIterator is the List-only upgrade: bidirectional, plus add(), set(), nextIndex().
    • A Map is not Iterable — you iterate entrySet(), keySet() or values().
    14

    I/O, enum, casting

    60s

    The last sweep — short answers, quick marks

    • The input chain: new BufferedReader(new InputStreamReader(System.in)) — System.in gives raw bytes, InputStreamReader decodes them to chars, BufferedReader adds a buffer and readLine().
    • readLine() always returns a String, so you parse it yourself: Integer.parseInt(br.readLine()).
    • BufferedReader vs Scanner: BufferedReader is faster and buffered but has no parsing; Scanner parses tokens for you but is slower. Use BufferedReader for competitive input.
    • throws IOException exists because it is a checked exception — the compiler forces you to catch it or declare it. Unchecked (NPE, ArithmeticException) needs neither.
    • enum is a class extending java.lang.Enum, so it cannot extend anything else. Gives you values(), ordinal(), valueOf(), and type safety that int constants never had.
    • Casting: widening is implicit and safe; narrowing needs an explicit cast and can silently overflow. For objects: upcast is implicit, downcast is explicit and can throw ClassCastException — guard with instanceof.
    Note the boundary: exceptions appear here only as "checked vs unchecked", because that is all your I/O notes cover. The full hierarchy, custom exceptions and try-with-resources are course sections #43–44 — still ahead of you.
